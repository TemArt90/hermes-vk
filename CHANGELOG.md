# Changelog

## 1.14.0 — 2026-10-04

- **`/model` стал интерактивным: провайдер → модель кнопками.** Половина этой возможности уже была в
  ядре: `gateway/slash_commands_model.py` вызывает `adapter.send_model_picker(...)` и падает на текстовый
  список, если у типа адаптера такого метода нет (проверка идёт по **типу**: `getattr(type(adapter), …)`).
  Теперь метод есть, как у Discord и Matrix, и `/model` без аргументов приходит клавиатурой. Логика
  переключения, cost-guard и текст подтверждения остались ядровыми — адаптер только рисует и передаёт выбор.
- **`/reasoning` и `/fast` тоже стали кнопочными** — им нужен второй метод того же контракта,
  `send_choice_picker` (плоский список «значение → тап»).
- **Раскладка под замеренный предел VK:** 7 позиций на страницу (2 в ряд) плюс ряд управления из трёх
  кнопок — ровно 10, потолок inline-клавиатуры. Живой замер на реальных данных: 6 провайдеров встают на
  одну страницу, у самого крупного (OpenCode Zen, 116 моделей) — 17 страниц по 7; текущие модель и
  провайдер помечены точкой.
- **Замерено и используется: правка с пустой клавиатурой снимает кнопки** — `messages.edit` с
  `{"inline": true, "buttons": []}` оставляет сообщение без клавиатуры (`messages.getById` отдаёт
  `keyboard: null`). Так результат выбора заменяет список, не оставляя мёртвых кнопок.
- **Безопасность как у остальных кнопок:** нажимает только тот, кого пропускает `VK_ALLOWED_USERS`,
  выбор работает только в том чате, где показан; payload кнопки сверяется со списком, который реально был
  показан (чужая/устаревшая модель → «Модель недоступна», колбэк ядра не вызывается); после выбора
  повторное нажатие отвечает «Выбор уже сделан».
- **Состояние выбора — в памяти, в отличие от виджетов:** выбор живёт 15 минут и умирает вместе с
  процессом, потому что колбэк — это замыкание ядра; после рестарта шлюза старое сообщение честно скажет
  «Выбор устарел», а не вызовет мёртвое замыкание.
- Тесты: 209 (26 новых: контракт `SendResult`, отрисовка и границы VK, страницы и «назад», TTL и лимит
  записей, отказ чужому чату, чужая модель/вариант, подтверждение дорогой модели, падение колбэка).
  Проверено мутацией: снятие маршрутизации, `resolved` и проверки «модель была в списке» роняют 12 тестов.

## 1.13.0 — 2026-10-04

- **Интерактивные списки в чате (`vk_checklist`) — новый слой «виджетов».** Сообщение с кнопками-позициями:

- **Замерено на живом сообществе (04.10.2026): у inline-клавиатуры жёсткий предел 10 кнопок.**
  11-я кнопка — не «лишняя», а отказ всего вызова: ошибка 911 `Keyboard format is invalid: keyboard
  contains too much buttons`, сообщение не уходит. Отсюда раскладка виджета: 8 позиций на страницу
  (4 ряда по две) плюс ряд перелистывания = ровно 10; список до 10 позиций обходится без перелистывания.

  чтением назад через `messages.getById`, который отдаёт inline-клавиатуры). Без этого виджет не смог бы
  перерисовывать отметки на месте: правка идёт простым текстом (`format_data` у `messages.edit` нет),
  поэтому тело виджета — только ☐/✅ и emoji.
- Доступ остался штатным: виджет отвечает только тому, кого пропускает `VK_ALLOWED_USERS`, и только в том
  чате, куда его отправили (чужой `peer_id` в payload → «Список устарел», состояние не двигается).
- Тесты: 183 (27 новых — состояние и рендер, границы клавиатуры, перелистывание, владение чатом,
  путь нажатия с отказом и с падением правки, инструмент, регистрация на контексте плагина). Проверено

## 1.12.0 — 2026-10-04

- **Нативное видео заработало на пути cron/`hermes send` — дефект найден живой проверкой.** Личный ключ

  `user_token`, поэтому `video.save` уходил ключом сообщества. Теперь ключ читается через
  `extra_or_secret(extra, "user_token", "VK_USER_TOKEN")` и передаётся конструктору. Проверено живьём
  после фикса: вложение пришло типом `video` (`13580122_456239053`), новых отказов в документ нет.
- **Вложение приватного видео теперь несёт `access_key`.** Замерено: `video.save` возвращает
  `access_key`, а `video<owner>_<id>` без него оставляет получателю плеер, который отказывается играть
  приватное видео — то есть «нативная отправка» была бы хуже документа. Формат вложения стал
  `video<owner>_<id>_<access_key>` (при наличии ключа). Проверено живьём: `access_key` присутствует в
  объекте вложения в `messages.getHistory`.

  прямых ссылок на файлы VK больше не выдаёт. `direct_url` из ответа — не файл, а HTML-страница плеера
  (`vkvideo.ru`, скачанные 103 525 байт без единого байта mp4). Права «Видео» этого не меняют, поэтому
  входящее видео остаётся пометкой `[видео: <название>, <длительность> с]` при любом ключе, и обещание
  «скачивается агенту» убрано из манифеста и README. Личный ключ нужен ровно для одного: нативной
  отправки исходящего видео.
- Тесты: 156 (две новые проверки — путь cron передаёт личный ключ конструктору; вложение сохраняет

  не теряет сообщение; выключенный приём вложений не тратит личный токен; `video.get` и `video.save` идут
  именно личным токеном; маскирование токена; личный токен без ключа сообщества не делает платформу
  готовой; изоляция профилей расширена личным токеном. Мутации подтверждают зубастость.

## 1.9.0 — 2026-10-03

- **Окно дедупликации стало настраиваемым** (`VK_DEDUPE_TTL_SECONDS`, по умолчанию `900` — как было).
  Имя переменной взято у родственного VK-плагина, чтобы миграция была в одну строку; семантика — своя,
  осознанно: `0`, отрицательные, мусор и значения меньше 30 возвращают умолчание, а **не** выключают
  дедупликацию, как это читается у них. Выключенная защита означает повторный ответ агента на
  переотправленное VK сообщение — цена такой ошибки выше удобства отладочного переключателя.
- **Изоляция профилей теперь проверяется тестами** (всего 117, +11). Шесть инвариантов живут в наборе
  адаптера: секреты читаются только через `get_scoped_secret`, `os.environ` для `VK_*` не используется,
  профиль без своего токена закрыт (а не падает), две «сессии» получают каждый свой токен, окружение не
  мутируется при создании адаптера. Плюс сквозная проверка в подпроцессе через тот же API скоупинга,
  которым пользуется ядро (`set_secret_scope` + `build_profile_secret_scope`) с включённым
  мультиплексированием: профиль без токена не заимствует соседский, не засеивает cron-канал, а
  `VK_TOKEN` из окружения процесса игнорируется. В CI сквозная проверка пропускается с печатью причины
  (там срез зависимостей, а не полный рантайм) — пропуск видно, он не выглядит как успех.
- Сквозной тест переписан ради времени: первый вариант тянул настоящий менеджер плагинов в трёх профилях —
  147 с на один тест; версия на API ядра обходится 0,35 с, полный прогон набора — 16 с.

## 1.3.0 — 2026-10-03

- Добавлено: **правка сообщений на месте** (`messages.edit`). Длинные ответы и прогресс больше не
  приходят вторым сообщением — ядро обновляет уже отправленное. Учтены два ограничения VK: у
  `messages.edit` нет `format_data`, поэтому правка идёт простым текстом (`to_plain`; разметка живёт
  только в исходной отправке), и правка не умеет разбивать — содержимое, не влезающее в одно
  сообщение, возвращается вызывающему с `success=False`, и он отправляет заново с обычной разбивкой.
- Добавлено: **реакции-подтверждения** (`VK_REACTIONS_ENABLED=true`, по умолчанию выключено): 👌 на
  входящее сообщение, пока агент работает, затем 👍 при успехе или 👎 при ошибке; отменённый запрос
  остаётся без реакции. Используются штатные хуки ядра `on_processing_start` /
  `on_processing_complete(event, outcome)`, которые gateway вызывает сам. Номера реакций
  настраиваются (`VK_REACTION_PROGRESS` / `VK_REACTION_OK` / `VK_REACTION_FAIL`, `0` отключает шаг) —
  VK нумерует реакции по сообществу.
- Учтено: реакции адресуются по **`cmid`** (`conversation_message_id`), а не по `message_id` — иначе
  VK отвечает ошибкой 100. Адаптер запоминает пару «чат + сообщение → cmid» на время обработки.
  Ошибки 1009/1010/1011 (нет такой реакции / отключена / предел) логируются и не мешают ответу;
  отсутствие `messages.deleteReaction` в старом API запоминается, и метод больше не дёргается.
- Тесты: 62 (было 50). Правка, адресация реакций и выключенность по умолчанию проверены мутацией:
  сломанная ветка роняет от одного до пяти тестов.

## 1.0.0 — 2026-10-03

Первая публичная версия. Канал ВКонтакте для Hermes Agent: Bots Long Poll на вход,
`messages.send` на выход, без вебхука и домена.

**Что входит**

- Транспорт: `groups.getById` → `groups.getLongPollServer` → `a_check` (wait=25, version=3),
  восстановление после `failed=1/2/3`, повтор с тем же курсором при транспортной ошибке
  (иначе VK молча пропускает события, накопившиеся за время обрыва).
- Разметка: Markdown → `format_data` (`bold`/`italic`/ссылки) с офсетами в UTF-16,
  allowlist типов (одна неподдерживаемая конструкция обнуляет весь `format_data`),
  нарезка под лимит VK, таблицы → «заголовок + пункты», цитаты → курсив.
- Медиа: приём фото/документов/голосовых в кэш агента; отправка через
  `photos`/`docs.getMessagesUploadServer`; подпись и вложение одним сообщением;
  голосовые — Ogg Opus через ffmpeg с деградацией в документ.
- Кнопки: inline-клавиатура + `message_event`, общая конвенция Hermes
  (clarify / подтверждение опасных команд / слэш-подтверждения), обязательный ответ
  на нажатие, отказ неавторизованным, одноразовость кнопок.
- Доступ: штатные гейты Hermes + pairing-код, без собственной логики allowlist.
- Доставка по расписанию: `deliver=vk` (в том числе в списке `email,vk`).

**Проверено**

- 32 автотеста (`pytest`), включая живой цикл на мок-сервере VK: `connect → long poll →
  входящее → send → disconnect`, обрыв соединения и восстановление сессии.
- Живым сообществом: маршрут «входящее сообщение → сессия агента → ответ»,
  разметка на проводе (`format_data` через `messages.getHistory`), загрузка картинки
  с подписью одним сообщением, доставка крон-отчёта.

**Чего в этой версии нет**

- Голосовые исходящие проверены только при наличии `ffmpeg`; без него файл уходит документом.
- Работа с «историями», опросами и другими типами вложений VK не поддержана.
